# 内存分配管理

公共接口位于 [main/base/memory.h](../main/base/memory.h)，实现在 [memory.cpp](../main/base/memory.cpp)。它负责显式选择内存区域，并记录已接入模块的基础用量；不替换系统 `malloc/new`，也不修改第三方库的分配器。

## 分配策略

| 策略 | 用途 | 回退行为 |
| --- | --- | --- |
| `kBalanced` | LVGL 等大小混合的普通对象 | 不超过 4 KB 的小分配优先高速内部 RAM，其余仅使用 PSRAM；内部余量不足时仅使用 PSRAM |
| `kFastInternal` | 明确需要快速访问的内部缓冲 | 仅普通高速内部堆，失败返回空指针 |
| `kPsram` | 图片、较大的业务缓存 | 仅 PSRAM，失败后由业务决定降级 |
| `kInternalDma` | 明确要求内部 DMA 的缓冲 | 仅内部 DMA 堆，允许使用系统 DMA 保留池 |

`kBalanced` 使用 `min(4096, CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL)` 作为大小分界。大于分界的普通分配仅使用 PSRAM，不再因为 PSRAM 不足而回退抢占内部连续内存。分配前检查普通内部堆余量，按 `CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL` 保留余量；本次分配可能低于该余量时只使用 PSRAM，避免界面对象耗尽 TLS AES 描述符和 SDIO 接收缓冲所需的内部 DMA 内存。这是普通分配的分流策略，不是对其他任务或第三方分配器的硬性预留保证。普通高速内部堆要求 `DEFAULT`、`INTERNAL`、`DMA` 和 `8BIT` 能力，在 ESP32-P4 上排除 RTC RAM/TCM，同时避开系统专用保留池。不要以“不够时分配到任意内部内存”替代这个限制，具体背景见 [WLAN 页面性能](wlan-performance.md)。

`kInternalDma` 只表示内存区域要求，不承诺满足所有外设的缓存行、对齐、连续长度或缓存同步要求。需要特殊对齐的显示、相机、USB 等驱动缓冲继续使用各自驱动接口，不应直接迁入普通分配接口。

## 使用方式

```cpp
#include "base/memory.h"

using namespace lilygo_box;

void* buffer = memory::Allocate(
    4096, memory::Policy::kPsram, memory::Module::kGeneral);
if (buffer != nullptr) {
  // 使用缓冲区。
  memory::Free(buffer, memory::Module::kGeneral);
}
```

- `AllocateZeroed` 校验元素数量乘法是否溢出，并清零申请范围。
- `Reallocate` 失败时返回空指针，原指针、原内容及存活用量保持有效；调用方先保存返回值，成功后再替换原指针。
- 零大小分配返回空指针，不算失败；对非空指针扩容到零等同释放。
- 所有接口仅在任务上下文调用，不支持 ISR；同一指针的并发访问由调用方协调。
- 申请、扩容和释放必须全部经过公共接口，并传入相同的 `Module`。不能用它释放其他分配器的指针，也不能绕过它直接 `free` 已计数的指针。

模块标签由调用方维护，不为每个分配增加块头或地址追踪表。因此它不会自动识别错误的模块标签、越界、重复释放或所有权错误。

## 当前接入范围

| 模块 | 接入内容 |
| --- | --- |
| LVGL | 链接包装 `lv_malloc_core`、`lv_realloc_core`、`lv_free_core` |
| Camera | 相机页面持有的预览图像缓冲；不包含硬件驱动的相机缓冲 |
| Radio | 聊天记录热缓存、会话状态数组，以及 P4/P4 Air 的 WLAN 扫描临时快照 |
| General / 应用连接 | 初始化凭证工作区、保存前的回滚快照和 TLV 编码缓冲，使用 PSRAM 并自动释放 |

LVGL 沿用大小分流，同时保护内部堆余量。设置页共享状态显式使用 PSRAM；页面删除时先完成子树回调和定时器清理，再释放共享状态。相机页面继续仅使用 PSRAM。Radio 聊天记录及会话状态仅使用 PSRAM；主缓存分配失败后在 PSRAM 中尝试较小容量，仍失败则返回失败，不再将大缓存搬回内部 RAM。

SDK、标准容器、驱动、TLS 及尚未接入的分配不包含在模块计数中，但会反映在系统堆快照中。模块用量之和不是整个程序的内存占用。

应用连接配置在启动时由默认 4 KB 栈的 `main` 任务读取。五份凭证及其解码副本如果作为局部变量保留在栈上，会与 NVS/Flash 的调用栈叠加，造成栈溢出。因此初始化工作区、回滚快照和 2 KB 编码缓冲通过统一内存工具申请 PSRAM，由局部独占对象自动释放；启动连接服务时直接读取到已有配置对象，避免按值返回产生大临时副本。初始化工作区申请失败时不发布空配置，更新所需缓冲申请失败时返回失败。

任务栈占用需要单独检查，不能根据堆剩余容量判断栈是否足够；上述临时缓冲移入堆后才会计入 `General` 的模块统计。

ESP-Hosted 任务栈通过 `CONFIG_ESP_HOSTED_DFLT_TASK_FROM_SPIRAM=y` 放入 PSRAM；启用 PSRAM 的设备上，应用连接 HTTPS 服务也通过 `httpd_config_t::task_caps` 将默认 10 KB 任务栈放入 PSRAM，栈大小和任务优先级保持不变。这些任务栈不包含在公共工具的模块统计中。以太网 DMA、SDIO DMA 和任务控制块仍按 SDK 的能力要求分配，避免音乐、WLAN、以太网和桌面连接同时运行时争用内部连续内存。

PSRAM 栈不能执行要求关闭 Flash 缓存的操作，否则会触发 `esp_task_stack_is_sane_cache_disabled()` 断言。HTTPS/WebSocket 回调只提交 OTA 取消请求：下载中由已有 OTA 任务处理；暂停或待安装时临时创建 6 KB 内部 RAM 栈的清理任务，恢复当前启动分区并删除更新标记和缓存，完成后释放任务。取消接口返回成功仅表示请求已接受，实际结果通过更新状态查询；任务创建失败时保留原阶段和固件缓存，返回失败并允许重试。旧连接凭证补记安装标识的 NVS 写入也由已有的内部 RAM 栈连接任务执行，认证回调只标记待保存状态，写入前重新检查授权是否仍然有效且未绑定。

ESP-IDF 5.5.4 的 HTTP 服务在任务创建失败后没有关闭已经创建的监听及控制 socket，首次可能只显示 HTTPS 服务启动后退出，后续持续报 `listen (112)`（地址已占用）。应用补充记录原本没有日志的 `ESP_ERR_HTTPD_TASK`，不要仅根据后续的地址占用错误判断为端口冲突。更新固件并重启后，验证各功能不同开启顺序下仍能看到 `Local discovery and encrypted WebSocket ready`，并实际完成桌面连接和心跳；编译通过不能替代该实机验证。

## 按需读取统计

```cpp
const auto snapshot = lilygo_box::memory::ReadSnapshot();
const auto& lvgl = snapshot.modules[
    static_cast<size_t>(lilygo_box::memory::Module::kLvgl)];
// lvgl.current_bytes、peak_bytes、live_blocks、failures

// 需要日志诊断时主动调用，不要放进高频绘制定时器。
lilygo_box::memory::LogSnapshot();
```

模块计数包括当前实际分配块字节数、历史峰值、存活块数和最终分配失败次数。实际块大小可能包含对齐产生的额外空间，不等于请求大小；统计不包括堆管理元数据，也不统计 `realloc` 内部搬迁的瞬时双份占用。计数从本次启动开始累积。

系统快照提供默认堆、全部内部堆、普通高速内部堆和 PSRAM 的总量、空闲量、历史最低空闲量和最大连续空闲块。总量减空闲量可用于观察该区域的堆占用；它不等同于固件全部静态及动态 RAM 的总和。各区域范围存在重叠，不能相加；最大连续空闲块有助于判断是否能容纳下一次大分配。多堆快照不是全系统原子采样，区域最低空闲量也不一定出现在同一时刻。

内存统计使用固定数组和短临界区，不创建统计后台任务或周期日志，也不添加界面。分配失败按模块在第 1、2、4、8 等次数记录项目日志，避免连续失败刷屏；首选区域失败但回退成功不算最终失败。


## 统一安全分配与任务创建（2026-11-13）

普通大缓冲优先使用 PSRAM，目的是给以太网 DMA、SDIO、TLS 内部描述符和任务控制块保留可用内部内存。分配成功与否还取决于最大连续块、对齐和能力要求，不能只判断总空闲容量，也不能通过统一接口保证所有场景永不失败。

### 普通缓冲与对象

普通业务新增代码使用 `memory::MakeBuffer<T>`、`memory::MakePsramObject<T>` 或底层 `Allocate/Reallocate/Free`。数组及普通业务对象默认仅使用 PSRAM；数组检查元素数量乘法溢出，独占指针自动释放，对象先析构再释放。硬件特殊对齐、DMA 缓冲仍由对应驱动专用接口管理。数组只支持平凡数据，对象构造必须不抛异常；对象内的标准容器仍使用各自分配器。

`MakeBuffer` 默认不清零。协议编码、读取缓冲可直接使用；依赖初值的结构应使用 `MakePsramObject<T>()` 进行值初始化，或显式传入 `zeroed=true`。空指针必须在传给读取、解码和复制函数前检查；分配失败时返回失败、结束任务或降低业务容量，不循环无限重试、不继续使用空指针、不静默占用内部大块。

本次接入：MP3 定位搜索和 VBR 头、GPS 文本临时数组、OTA 清单/散列/无线固件传输缓冲及清单对象、NVS TLV 读取和 WiFi/Radio/音乐配置编解码及大型配置快照、Radio 聊天记录读取/热缓存和会话状态。音频逐帧缓冲与输出队列按下述实时路径例外处理，使用 SDK 默认分配，不计入公共 General 模块用量。

MP3 环形缓冲容量、预缓冲阈值、优先级和播放顺序保持原值。MP3 普通缓冲分配失败会关闭解码器和文件；定位搜索分配失败会尝试恢复原文件位置。音乐扫描任务创建失败时保留现有曲库与播放状态，不在 UI 线程同步扫描，避免低内存时界面长时间卡住。显示旋转缓冲保持原缓存行对齐要求，但取消任意 8BIT 堆回退，仅使用 PSRAM。

### 任务栈与生命周期

公共入口位于 [main/base/task.h](../main/base/task.h)，实现位于 [task.cpp](../main/base/task.cpp)。应用自己的动态任务创建统一经过以下接口，不修改 SDK 内部创建任务的行为：

| 接口 | 栈和退出方式 | 使用场景 |
| --- | --- | --- |
| `tasks::CreateDetached` | 默认 PSRAM；入口必须正常返回，自动回收 | LoRa 命令/关闭、CIT IMU/GPS、音乐扫描、震动、P4 V1 以太网初始化 |
| `tasks::CreateManaged` | 显式栈区域；调用方保存句柄并从其他任务调用 `DeleteManaged` | P4 V1/V2 相机预览、常驻复用的 WLAN 初始化/扫描/连接任务 |
| `tasks::CreateInternal` | 内部栈；保留原 `xTaskCreate` 生命周期，仍用 `vTaskDelete` 退出 | 音频实时任务、NVS/Flash 写入任务、系统回调任务和暂未验证外部栈兼容性的任务 |

所有任务保留原栈大小、优先级和核心调度方式。任务控制块仍在内部 RAM。启用外部栈需要 `CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y`；静态回收服务需要 `CONFIG_FREERTOS_SUPPORT_STATIC_ALLOCATION=y`。未启用外部栈时，公共入口拒绝 PSRAM 请求；相机与 WLAN 调用方通过编译配置明确选择内部栈，其他外部栈任务报告失败，不在运行时偷偷回退。初始化由 `app_main` 在 `Application::Init` 之前完成。

`CreateDetached` 的入口不能调用 `vTaskDelete(nullptr)` 或 `vTaskDeleteWithCaps(nullptr)`，也不能由其他任务直接删除。正常返回会先析构局部智能指针和锁，再由公共入口移交回收。由静态内部栈（3072 字节）、静态控制块和 16 项静态队列组成的单个回收服务负责从外部删除任务；队列满时工作任务阻塞等待，不丢弃回收请求。任务执行结束后的回收不申请临时清理任务，避免 ESP-IDF 5.5.4 的自删 WithCaps 任务路径在低内存时因清理任务创建失败触发断言。

创建失败时，业务参数仍由调用方持有和释放；成功后才交给任务。统一入口记录任务名称、栈大小、区域以及内部 RAM/PSRAM 的空闲量和最大连续块。PSRAM 分配失败不回退为内部栈。

本次同时修复 Radio 关闭及音乐扫描任务直接自删跳过局部智能指针析构的资源泄漏。P4 WLAN 的三个请求任务平时复用，空闲时阻塞；内存不足时可自动回收空闲任务，下次请求时重新创建，避免平时每次扫描/连接都重新申请 6 KB 栈；相机在明确完成后由持有者回收，保持原有停止同步。

### 必须保留内部内存的部分

- OTA 下载/安装/取消清理、LittleFS/NVS 写入、指南针校准保存、应用连接凭证保存，以及会执行设置保存的 UI 任务仍使用内部栈。
- USB 主机/扩展坞、NFC、键盘、快充服务、RTC 同步、网络监控、P4 Air WLAN/相机/蜂窝等未经完整外部栈调用链验证的任务保留内部栈，只接入统一失败诊断。不能因任务调用 DMA 驱动就直接断定栈必须内部，也不能未检查 SDK 回调链就直接迁往 PSRAM。
- 以太网 RX/TX DMA、SDIO DMA、I2S DMA、相机/显示的 DMA、缓存同步和对齐要求继续由各驱动满足。业务缓冲能够放入 PSRAM，不表示其底层 DMA 描述符也能放入 PSRAM。
- 不全局重载 `malloc/new`，不把所有内部内存都迁到 PSRAM。SDK、第三方库、标准容器以及它们的嵌套分配仍需遵守原能力约束，不全部纳入模块统计。

### 检查要求

新增大缓冲先选择区域并检查失败，成对匹配分配与释放；新增外部栈任务先检查是否存在 Flash/NVS 写入以及依赖缓存关闭的调用链。不要通过增加重试次数掩盖持续分配失败，不改变音频优先级来补偿内存问题。

主机验证可检查分配失败、数量溢出、对象析构、任务创建失败、正常退出和集中回收；固件编译检查板型条件分支。最终仍需在实机上反复启停 WLAN、应用连接、以太网、音乐、LoRa、CIT 和相机，检查最大内部连续块和是否存在累计泄漏；主机模拟和编译不能确认生产板的偶发故障已经消失。

2026-11-13 检查记录：P4 V1、P4 V2、P4 Air 均完成固件编译；公共实现的主机模拟通过 4,100 次临时任务创建与回收，并覆盖回收队列压力、任务创建失败、分配失败、数量溢出、对象析构和扩容失败保留原数据。另对实际 MP3 缓冲申请代码及输出类模拟单声道/立体声各分配阶段、信号量和任务创建失败，确认文件、解码器、环形缓冲及普通缓冲释放。当前音频实现另覆盖普通数组、环形队列控制/数据、信号量及任务创建失败的释放路径，并验证正常播放无新增日志、队列超时、输出间隔、暂停等待和 5 秒日志限频。主机桩只验证应用逻辑，不模拟 ESP32 双核内核调度和真实 DMA/Flash 时序。

### 音频实时路径的例外（2026-11-13）

音频使用与此前播放正常版本一致的 SDK 分配方式：P4 V1/V2/Air 的解码、输出、提示音和麦克风任务通过 `CreateInternal` 使用内部栈；MP3 读取缓冲（8 KB）、PCM 解码缓冲（16 KB）、发送缓冲（4104 字节）和单声道转换缓冲通过不抛异常的普通 `new[]` 申请。64 KB 输出队列恢复 `xRingbufferCreate`，控制结构和存储分别由 SDK 分配，结束时由 `vRingbufferDelete` 释放。不要再把队列控制结构改到播放栈，或将所有实时缓冲强制放入某个内存区。最终落点由 SDK 默认分配策略和当时可用连续块决定；PSRAM 有空闲不代表内部栈或 DMA 一定能够分配成功。

此前强制 `kFastInternal` 时，实机出现该能力堆最大连续块仅 184 字节、16 KB PCM 申请失败；随后强制 PSRAM 的版本仍反馈卡顿。因此恢复完整的原分配方式，并保留所有失败检查与资源释放，不能把“申请成功”当成“播放流畅”。定位搜索大缓冲继续使用公共 PSRAM 接口。优先级、栈大小、I2S DMA、64 KB 队列容量和 16 KB 预缓冲阈值保持原值，其他模块的 PSRAM 策略和空闲任务回收继续使用。

已对照本项目依赖的乐鑫 `esp_audio_codec 2.4.1` [官方解码测试](https://github.com/espressif/esp-adf-libs/blob/4d5cbe02f59fb45e40112d63317a8ddd00019cd4/esp_audio_codec/test_apps/audio_codec_test/main/audio_decoder_test.c)：其输入/PCM 缓冲使用普通 `malloc`，分帧调用解码器；ESP-IDF 5.5.4 [ES8311 播放示例](https://github.com/espressif/esp-idf/blob/v5.5.4/examples/peripherals/i2s/i2s_codec/i2s_es8311/main/i2s_es8311_example.c) 使用普通内部栈任务向 `i2s_channel_write` 写数据。SDK 会将源数据复制到驱动 DMA 缓冲，业务 PCM 缓冲不需要直接满足内部 DMA 能力；官方示例本身不证明本项目的并发场景已经流畅。

为定位实机剩余停顿，输出任务只累计队列接收超时（10 ms）和连续两次输出写入之间超过 40 ms 的间隔。生产任务在补足约 16 KB 预缓冲后记录 `MP3 timing`；持续缺数据达到 100 次接收超时时也允许记录，每 5 秒最多一次。日志包含读卡、解码、发送队列等待、输出写入、输出间隔的最大耗时（微秒），以及输入/PCM/发送缓冲、环形队列控制结构和两任务栈的参考地址。明显的暂停等待和主动定位切换不计为输出间隔；队列接收超时不等同于已发生可听见的断音。耗时包含等待和调度抢占，不能直接解释为 CPU 运算时间。正常无异常事件时不新增周期日志，不在输出任务中申请日志资源或打印。

固件编译和主机桩验证只覆盖接口、分配失败清理与诊断行为；真实播放时延仍需在 WiFi、应用连接、以太网和音乐同时开启时确认。

### 分配不足时自动回收后台任务

公共 `Allocate`、`Reallocate`、`CreateInternal` 和 `CreateManaged` 最终分配失败后调用 `TryReclaim`：使用启动时注册的固定回收器列表，不额外申请回收任务；回收成功后按原区域、能力和栈大小重试一次，仍失败则返回原失败路径，不无限循环，不改变 DMA 或高速内部内存约束。系统或第三方库直接调用 malloc/new 的失败不会自动触发此流程。数量溢出和无效参数直接失败，不触发回收。

回收顺序先同步清理统一回收队列中已经完成的任务，再检查 P4 V1/V2 的 WiFi 初始化、扫描和连接工作任务。WiFi 工作任务必须同时满足独立空闲标志为真、FreeRTOS 状态为阻塞等待，且能立即取得创建/唤醒共用的互斥锁，才能删除并清空句柄；业务 RPC 阻塞、正在初始化、扫描或连接的任务不会仅因阻塞状态被误删。WiFi 驱动和当前连接不关闭，下次请求自动创建被回收的工作任务。

回收入口仅在启动阶段注册，参数对象必须与应用同寿命。回调不得分配新资源，不得阻塞等待业务锁，不得删除活动任务、取消播放、写入 Flash 或破坏待保存数据；并发和递归回收会直接跳过。空闲 WiFi 栈主要释放 PSRAM，控制块释放内部 RAM；这不能保证得到特定大小的内部连续 DMA 块。暂不通过强杀活跃任务解决 DMA 碎片不足。

本次回收验证：使用实际公共分配实现及 WiFi 回收/创建函数的主机模拟，覆盖回收后申请成功、无资源可回收、递归回收跳过、扩容保留数据、锁忙时跳过，以及活动/RPC 阻塞/已唤醒/当前任务不被删除；空闲任务删除后下一次请求能够重建。音频的单声道、立体声及分配失败释放路径重新验证。主机模拟不验证播放流畅度，仍需实机确认。

播放输入信息在文件、解码器、缓冲和输出任务都准备成功后再打印。音乐状态定时器在 `kError` 时停止播放，不自动重启同一首歌；内存回收仅对一次失败的分配进行有限重试，不调用音乐播放入口。
