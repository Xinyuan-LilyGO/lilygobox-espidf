# WLAN 页面性能

## 问题与修复重点

ESP32-P4 上，WLAN 扫描得到列表后可能出现明显的页面滚动卡顿。排查中，主要耗时集中于 LVGL 渲染；同类模拟列表在未启动 Wi-Fi 时流畅，限制界面动画并未消除真实 Wi-Fi 场景下的问题。

有效修复是约束 LVGL 的内存分配区域：小对象优先分配到高速内部 RAM，内部内存不足时回退到 PSRAM，避免落入访问较慢的 RTC RAM。真实 Wi-Fi 场景的测试改善支持这一判断，不能仅因为启用 Wi-Fi 后出现卡顿，就归因为 ESP-Hosted 库本身有缺陷。

## 内存分配策略

分配策略集中在 [main/base/memory.cpp](../main/base/memory.cpp)，由 [main/hal/lvgl_memory.cpp](../main/hal/lvgl_memory.cpp) 接入 LVGL。[main/CMakeLists.txt](../main/CMakeLists.txt) 包装 `lv_malloc_core`、`lv_realloc_core` 和 `lv_free_core`，在保持内存策略的同时统计分配及释放，不修改托管的 LVGL 依赖。公共接口见[内存分配管理](memory-management.md)。

| 内存类型 | 能力约束 | 用途 |
| --- | --- | --- |
| 高速内部堆 | `DEFAULT \| INTERNAL \| DMA \| 8BIT` | 小对象的首选区域 |
| 外部 PSRAM | `DEFAULT \| SPIRAM \| 8BIT` | 大分配的首选区域、小分配的回退区域 |

上述名称对应 ESP-IDF 的 `MALLOC_CAP_*` 标志：

- `DMA` 在此用于排除 ESP32-P4 的 RTC RAM/TCM，不表示所有 LVGL 对象都要进行 DMA 传输。
- `DEFAULT` 避免占用系统专门为 SDIO 等用途保留的内部/DMA 内存池。
- 大小分界继续使用 `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL`；大分配先尝试 PSRAM，小分配先尝试高速内部堆。
- 首选区域分配失败时尝试另一种区域；扩容遵循同一策略。释放通过公共接口扣除模块统计，再调用系统堆释放函数，不得绕过公共统计入口。

包装仅在 ESP32-P4 且 LVGL 使用 C 标准库内存分配器时启用。更换 LVGL 分配器、链接配置或 ESP-IDF 版本后，需要重新确认包装入口和内存区域能力标志。

## 状态读取与页面刷新

另一项保留的改进是避免在界面线程发起同步 Wi-Fi RPC：

- `ReadWifiStatus` 读取本地状态快照。
- 后台网络监控调用 `RefreshWifiSignal` 更新信号信息，扫描期间跳过该查询。
- 连接事件缓存 SSID、信道等数据，连接代次校验避免异步查询结果覆盖新连接状态。
- WLAN 页面只在信号文本或刷新图标角度改变时更新控件，减少无效重绘。

这部分用于防止网络查询阻塞界面，内存分配策略则是本次渲染卡顿的主要修复。它们解决不同环节的问题，应一起保留。

## 回归检查

1. 冷启动后进入 WLAN 页面，开启 Wi-Fi，并立即退出页面。
2. 等待后台扫描或连接，再次进入 WLAN 页面并上下滚动。
3. 在扫描中、连接中及获得网络地址后分别检查滚动和触摸响应。
4. 重复退出、进入和重新扫描，确认长名称滚动与 5 GHz 标签正常。
5. 检查自动连接、关闭 Wi-Fi、应用连接和其他页面切换是否正常。

测试必须使用真实 Wi-Fi 扫描列表。进一步定位时，应区分渲染耗时、RPC 等待、后台任务占用和内存分配位置，避免只依据总体 CPU 使用率判断原因。

正式代码不保留本次排查使用的模拟热点、逐绘制函数计时和周期性能输出。后续临时加入诊断时，验证后应移除，不改变正常界面样式和功能。
